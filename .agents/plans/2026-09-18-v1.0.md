# Apple Interview Practice Deck

## Summary

Build a focused Vue interview-practice experience containing 20 questions derived from the shared conversation. Organize them into six categories and use a “speak, reveal, rate” loop:

1. Read the prompt.
2. Answer aloud with an optional timer.
3. Reveal key story beats, a polished sample response, and a likely follow-up.
4. Rate confidence as “Needs work,” “Getting there,” or “Ready.”
5. Revisit weak cards later.

Users can practice one category or start a shuffled mixed session. Progress persists locally without accounts or a backend.

## Content and Categories

Create these 20 cards:

- Personal narrative and motivation
  - Tell me about yourself.
  - Why Apple?
  - Why Wallet, Payments & Commerce?
  - Why are you moving from independent product building back to a larger engineering organization?

- Product ownership and Sway
  - Tell me about something you built end-to-end.
  - How did user feedback change the direction of Sway?
  - What did shipping your own product teach you that you did not learn in a large organization?

- Leadership and collaboration
  - Tell me about a disagreement with another engineer.
  - Describe a technical decision where you changed your mind.
  - How do you balance engineering quality with delivery pressure?

- Production engineering and reliability
  - What is the most technically difficult problem you have solved?
  - Tell me about a production issue you debugged.
  - How do you handle failures from an external service?
  - How would you prevent duplicate or ambiguous payment operations?

- Frontend, API, and system design
  - How would you design an API between a transaction UI and its backend?
  - How do you approach frontend performance?
  - How would you test a payment-related system?
  - Design the high-level architecture for a product like Sway.

- Vue and team fit
  - How do your React and Next.js skills transfer to Vue?
  - Why might a payments team choose Vue instead of Next.js?

Each revealed answer will contain:

- Three to five concise beats the user should cover.
- A conversational 45–90 second sample response.
- One likely follow-up question.
- Guided placeholders such as `[system context]`, `[root cause]`, `[measurable result]`, and `[specific disagreement]` wherever the shared conversation lacks verified Capital One details.
- A reminder that placeholders must be personalized and that confidential employer information should not be disclosed.

Answers should rotate naturally among three complementary narratives: production-mature Capital One engineer, independent product builder, and systematic full-stack engineer. Preserve memorable ideas from the source conversation without making every response sound rehearsed or inspirational.

## Experience and Design

- Replace the Vue starter screen with a category library, active practice view, and compact results summary.
- Give each category a distinct restrained accent while maintaining one coherent visual system inspired by physical interview cue cards rather than a generic dashboard.
- Make the prompt the dominant element. Keep coaching hidden until reveal so recognition does not replace recall.
- Use a single purposeful card-turn or card-slide transition when revealing the answer. Respect reduced-motion preferences and avoid automatic decorative animation.
- Provide category selection, mixed practice, shuffle, previous/next controls, keyboard navigation, optional timer, progress count, and restart.
- After rating a card, prioritize “Needs work” cards when the user selects “Practice weak cards.”
- Persist ratings, completion state, timer preference, and last selected category in `localStorage`.
- Ensure the full flow works on mobile, supports keyboard focus, and uses semantic buttons and live status text.

## Interfaces and State

Define a typed content model similar to:

```ts
type CategoryId =
  'story' | 'product' | 'collaboration' | 'reliability' | 'architecture' | 'team-fit'

type Confidence = 'needs-work' | 'getting-there' | 'ready'

interface InterviewCard {
  id: string
  category: CategoryId
  question: string
  suggestedSeconds: number
  keyBeats: string[]
  sampleResponse: string
  followUp: string
  placeholders?: string[]
}
```

Keep the question deck as local typed data. Store only card IDs, ratings, preferences, and timestamps in persisted state so content can be edited without migrating saved copies of the answers. Validate restored data and fall back safely if local storage is unavailable or stale.

## Test Plan

- Unit-test category filtering, shuffled mixed sessions, weak-card prioritization, progress calculations, timer reset, and local-storage restoration.
- Component-test the prompt → reveal → confidence-rating → next-card flow.
- Verify that unrevealed cards do not expose answer content to sighted users or keyboard focus.
- Verify keyboard navigation and reduced-motion behavior.
- Test empty weak-card state, completed sessions, refresh persistence, malformed saved data, and category switching.
- Run `npm run test:unit -- --run` and `npm run build`; add a Cypress test for completing and resuming a short practice session.

## Assumptions

- The first version is a private, single-user preparation tool with no login, backend, recording, transcription, or automated AI grading.
- Responses are grounded only in the shared conversation; missing professional details remain explicit placeholders rather than invented claims.
- Spoken answers are self-assessed. The timer encourages concise delivery but never blocks revealing the coaching.
- The visual direction follows the repository’s `frontend-design` skill: subject-specific cue-card styling, one meaningful motion treatment, and restrained supporting UI.
